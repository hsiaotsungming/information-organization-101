建立 Knowledge Graph 的階段

將資料轉換為知識圖譜的六步驟工作流程。

1. 本單元目標 2. 六步驟工作流程 3. 領域理解 4. 資料理解 5. 表示形式 6. 本體匯入 7. 標註資料 8. 查詢與推理 9. 小練習

本單元目標

  • 理解建立知識圖譜時需要處理哪些領域、資料與模型層面的問題。
  • 說明將既有資料轉換為知識圖譜時，六個主要步驟之間的關聯。
  • 理解查詢與推理需求如何反過來影響知識圖譜的設計。

六步驟工作流程

建立知識圖譜（Knowledge Graph）需要處理領域需求、資料內容、表示形式、本體設計、標註資料等問題，並考慮查詢與推理需求，整合為一個完整的工作流程。過程中，是要將既有資料重新組織為具有語意關係、可查詢、可連結，並可支援推理的知識結構，之後才能將資料匯入圖資料庫。整個過程，可以分成六個步驟：

  1. 釐清領域理解（domain understanding）
  2. 進行資料理解（data understanding）
  3. 選擇圖表示形式（graph representation）
  4. 知識本體匯入（ontology ingestion）
  5. 標註資料匯入（annotation ingestion）
  6. 驗證查詢與推理能力（querying and reasoning）

要將資料轉換為知識圖譜，不是單純將資料表改寫圖資料庫，而是要將目前的資料表、欄位、標註與詮釋資料，透過本體與模型重新組織為具有語意關係的知識網絡。

釐清領域理解

第一步是釐清領域理解。在建立知識圖譜之前，需先確認此一知識圖譜要服務的問題與使用情境。例如，這個知識圖譜是要支援查詢、推理、推薦、資料整合，還是作為大型語言模型（Large Language Model, LLM）的知識依據層（grounding layer）。

若目標是推薦，因為推薦要判斷東西和使用者有多相關，可能需要重視使用者、物件、主題與行為之間的關係，才能知道同一個東西為什麼適合 A，卻不一定適合 B。若目標是資料整合，因為資料整合要判斷不同來源的資料是否指向同一個對象，可能需要重視不同資料來源之間的識別、對應與一致性，才能知道兩筆看起來不同的資料其實是否在描述同一個人、同一件事或同一個物件。若目標是大型語言模型的知識依據，因為我們需要讓模型生成的回答有明確根據，可能需要重視來源、脈絡、可追溯能力，以及查詢結果是否容易被模型取用，才能讓回答可檢查、可更新，也比較不容易脫離原意。

在這個階段，要處理的核心問題是：這個知識圖譜要幫使用者回答什麼問題？建立知識圖譜前，可以先列出一組能力問題（competency questions），也就是這個圖譜完成後應該能回答的代表性問題。例如，目錄系統的任務有：

  1. Find：需要能夠依照作者、題名、主題或其他條件，尋找符合需求的資源。
  2. Identify：需要能夠識別找到的資源，並將它與相似或容易混淆的資源區分開來。
  3. Select：需要能夠判斷某項資源的版本、語言、形式或內容是否符合自己的需求。
  4. Obtain：需要能夠取得或存取所選資源，例如借閱、下載、線上閱讀或取得館藏位置。
  5. Explore：需要能夠透過資源、作者、主題或其他實體之間的關係，進一步探索相關內容。

這些問題會決定需要建立哪些實體、關係、屬性的模型。若沒有先定義使用情境，知識圖譜很容易只是將資料表轉換成節點與邊，但缺乏處理使用者問題的能力。

進行資料理解

結構化資料通常包含是表格與欄位所組成，這些是為了儲存、管理或檢索而設計。需要進一步判斷這些欄位在知識結構中代表什麼意義後，才能形成知識圖譜。這包括檢視分類碼、詮釋資料架構（metadata schema），或是檢視主鍵、外鍵等。

建構時需要先理解每個欄位的角色，判斷它應被視為實體、屬性，或實體之間的關係。例如，在一筆書目資料中，作者、出版者、主題與出版年等欄位，可以分別被重新理解為圖書、人物、出版者、主題等實體，也可以被轉換為「撰寫」、「由某出版者出版」、「具有主題」等關係。出版年則可能只是圖書的屬性，也可能在特定研究情境中被轉換為時間節點，用來支援年代、時期或歷史脈絡分析。

也就是說，建構時不是只問要不要匯入某個欄位，而要問在知識圖譜中應該如何被表達。例如：

  1. 作者欄位：若需要被識別、區分、合併或連結到其他資料，則可將其視為可辨識的人物實體。
  2. 主題欄位：若需要呈現階層、關聯、同義詞或概念脈絡，則可將其視為主題概念體系中的節點。
  3. 出版者欄位：若需要連結到機構、出版活動或歷史脈絡，則可將其視為更廣泛出版關係中的一部分。
  4. 年分欄位：若需要用來區分版本、描述事件順序、建立時間脈絡或連結到特定時期，則可將其視為具有分析意義的時間資訊。
  5. 地點欄位：若需要被識別、區分、標準化，或連結到機構、事件、出版活動與歷史脈絡，則可將其視為可辨識的地點實體。

此外，建立知識圖譜前，需要檢查資料的品質，像是是否有重複名稱、異名、缺漏值、不一致的分類、不同來源之間的編碼差異，以及同名異人或同名異物等問題。若這些問題未先處理，匯入後的知識圖譜可能會形成錯誤連結，使查詢與推理結果失真。

選擇圖表示形式

常見的圖表示形式包括資源描述框架（Resource Description Framework, RDF）與標籤屬性圖（Labeled Property Graph, LPG）。這兩者都能用來表示實體與關係，但其設計理念與適合的應用情境不同。

資源描述框架較接近語意網與本體的傳統，強調以三元組表示資料，也就是主詞、述詞與受詞的結構。其優勢在於標準化、可交換性、跨系統整合，以及與本體推理的結合。資源描述框架知識圖譜通常會搭配資源識別碼、RDFS、OWL、SPARQL 等技術，使資料具有較明確的語意基礎，也較適合需要跨資料來源交換、連結與推理的情境。

SPARQL
SPARQL 是用來查詢 RDF 資料的查詢語言，適合處理以「主詞—述詞—受詞」形式表達的資料。它常用於知識圖譜、鏈結資料與語意網環境中，用來查詢實體之間的關係、屬性與路徑。

標籤屬性圖則常見於 Neo4j 等圖資料庫，以節點、關係、標籤與屬性作為主要建模單位。它的優點是直覺、彈性高，容易進行互動查詢、路徑分析、圖演算法與應用開發。相較於資源描述框架，標籤屬性圖通常更貼近工程實作與產品開發需求，適合需要快速建構查詢服務、推薦系統、風險分析、知識探索介面或 GraphRAG 應用的情境。

Neo4j
Neo4j 是一套以圖形資料模型為核心的圖形資料庫系統，常用來儲存與查詢節點、關係與屬性所構成的資料。它採用標籤屬性圖模型，適合處理人物、組織、地點、主題、事件或物件之間的連結關係，並可透過 Cypher 查詢語言探索資料中的路徑、模式與關聯。

標籤屬性圖（Labeled Property Graph, LPG）
標籤屬性圖是一種以節點、關係與屬性來表示資料的圖形資料模型。節點和關係可以帶有標籤，並附加鍵值形式的屬性，因此適合描述人物、物件、事件與行為之間的關係。

在選擇圖表示形式時，除了考慮技術偏好外，也可以考慮以下目標。若重視標準化、本體推理、跨系統交換與長期資料互通，資源描述框架通常較為合適。若重視應用查詢、圖分析、工程實作與系統互動，標籤屬性圖可能較為方便。實務上也不一定只能二選一，有些系統會以資源描述框架管理語意標準與本體層，再將資料轉換到圖資料庫中支援應用查詢與分析。

知識本體匯入

知識本體在知識圖譜中扮演知識骨架的角色，負責定義有哪些類別、類別之間有什麼關係、哪些屬性合法，以及概念之間的上下位、等價或限制關係。如果資料是知識圖譜的內容，本體則是讓這些內容能被一致理解與組織的結構。

例如，在書目知識圖譜中，本體可能會定義圖書、作者、出版者、主題、出版事件、地點等類別，也會定義「作者撰寫作品」、「作品由出版者出版」、「作品具有主題」、「出版事件發生於某時間」等關係。資料匯入時，每一筆書目資料就不再只是孤立紀錄，而是被接到這套知識架構中。

本體匯入的價值在於，它能讓知識圖譜不只是節點與邊的集合，而是具有語意約束與領域邏輯的結構。例如，若本體定義「期刊論文」是「學術作品」的一種，系統就可以透過推理知道所有期刊論文也屬於學術作品。若本體定義某些屬性只能連接特定類別，則可以用來檢查資料是否出現不合理關係。

初期來說，較好的做法通常是先依據使用情境建立一個可用的核心本體，定義最重要的類別、關係與屬性，再隨著資料匯入、查詢測試與應用需求逐步擴充。過度龐大的本體可能會增加建置成本，也可能讓資料對應變得困難。

進行標註資料匯入

標註資料匯入指將資料中的標註、分類、對應結果、辨識結果或詮釋資料，轉換為知識圖譜中的節點與邊。例如，一份文件的紀錄中可能有主題標籤、人物標註、機構標註、時間標註或地點標註。這些標註資料可以被連接到文件，也可以進一步連接到其它的人物、機構、時間、地點與主題概念等實體。如此一來，文件就不只是全文資料，而是進入一個更大的知識網絡。使用者可以查詢某個人物出現在哪些文件中，也可以查詢某個主題與哪些機構、事件或地點相關。

匯入時的另一個重點是進行消歧義。不同資料來源可能使用不同名稱指稱同一個實體，例如作者姓名可能有縮寫、全名、不同語言譯名，機構名稱也可能有舊名、新名與簡稱。若不處理這些對應關係，知識圖譜中可能會出現多個其實指向同一對象的節點。反過來說，同一個名稱也可能指向不同實體，例如同名作者、同名地名或同名機構，因此需要透過識別碼、上下文、時間、來源或其他屬性進行區辨。

在標註資料匯入中，是把「對資料的描述」轉換為「可查詢的知識」。結構化資料提供了像是分類、標籤、詮釋、來源等資訊，而知識圖譜可以使標註不只是附屬欄位，而是能與其他實體形成關係的知識節點。這一步在大型語言模型與知識圖譜結合的情境中特別重要，這提供可以透過標註、抽取或對應來形成的知識連結。

設計與驗證查詢與推理

在建立的過程中，可以不斷透過查詢問題來檢查模型的表現是否合理，這是檢驗圖模型是否有效的重要方式。例如：

  1. 是否能查出某位作者相關的主題？
  2. 是否能沿著關係找到同一研究領域中的作品？
  3. 是否能找出某個主題在不同年代的發展？
  4. 是否能根據本體推理出某些隱含分類？
  5. 是否能讓大型語言模型透過檢索取得足夠明確且可追溯的知識片段？

這些查詢問題除了用來判斷前面的實體、關係、屬性與本體設計是否足以支援實際需求，也可以幫助發現模型設計上的問題。如果查詢結果不自然，或需要非常複雜的查詢才能得到基本答案，通常表示設計方式可能仍待改善。例如，某些設計成屬性的資訊，實際上應該被設計成節點。或著是某些關係可能太籠統，導致查詢時無法區分不同語意。某些類別可能切得太細，造成資料稀疏，也可能切得太粗，導致推理與分析不夠精確。

查詢通常是找出圖中已經明確存在的資料，推理則是根據本體、規則或語意約束，產生或辨識圖中未直接寫出的隱含知識。例如，若本體中定義博士論文是學位論文的一種，而某筆資料被標示為博士論文，系統就可以推得它也是學位論文。若定義某機構隸屬於某大學，而某作者任職於該機構，也可能進一步推導出作者與該大學之間的關聯。這類推理能力使知識圖譜不只是資料連結工具，也成為知識組織與語意擴展的基礎。

小練習

  1. 請用自己的話說明建立 Knowledge Graph 為什麼需要先確認資料來源與範圍。
  2. 請舉一種你熟悉的資料，說明其中可能有哪些實體與關係可以被抽取。
  3. 請說明如果沒有驗證與修正步驟，知識圖譜在後續查詢或應用上可能出現哪些問題。
